# First Specialized Adapter Candidate — AE2 (Design Only)

**Status:** Candidate; **no adapter compiled, loaded or runtime-tested**. API evidence is specifically AE2 **v26.1.13-beta** targeting Minecraft **26.1.2**, with NeoForge 26.1. This is a conditional implementation contract, not a representation that the proposed bridge, gateway, permission verifier, staging buffer or durability protocol already exists. See [ADR-0003](../decisions/0003-capability-driven-integration-ports.md), [contract](contract.md) and [unrun matrix](verification-matrix.md).

## Upstream boundary and non-permissions

AE2's tagged [`ICraftingService`](https://github.com/AppliedEnergistics/Applied-Energistics-2/blob/v26.1.13-beta/src/main/java/appeng/api/networking/crafting/ICraftingService.java) offers asynchronous plan calculation and job submission. Its tagged [`ICraftingRequester`](https://github.com/AppliedEnergistics/Applied-Energistics-2/blob/v26.1.13-beta/src/main/java/appeng/api/networking/crafting/ICraftingRequester.java) delivers output through `insertCraftedItems(link, key, amount, mode)` **while the job is running**; `jobStateChange(link)` signals completed/cancelled state and a link that is thereafter dead. `getRequestedJobs()` exposes requester links for reconnection. Tagged [`ICraftingLink`](https://github.com/AppliedEnergistics/Applied-Energistics-2/blob/v26.1.13-beta/src/main/java/appeng/api/networking/crafting/ICraftingLink.java) exposes cancellation, done state, crafting ID and serialization; a link is not a delivery receipt. Tagged [`Actionable`](https://github.com/AppliedEnergistics/Applied-Energistics-2/blob/v26.1.13-beta/src/main/java/appeng/api/config/Actionable.java) separates `SIMULATE` and `MODULATE`.

**Do not plan around an AE2 security station or a grid-ownership check as a reliable enforcement mechanism.** AE2's [security-system removal discussion (#7116)](https://github.com/AppliedEnergistics/Applied-Energistics-2/issues/7116) records retirement of that old protection model. This history does not establish the absence of every authorization check in the tagged implementation. Tagged [`IActionSource`](https://github.com/AppliedEnergistics/Applied-Energistics-2/blob/v26.1.13-beta/src/main/java/appeng/api/networking/security/IActionSource.java) supplies player/machine provenance, **not independent authorization** for enrollment, stock read, extraction, crafting or receiving crafted output. `IActionSource.empty()`, `ofPlayer(...)`, and `ofMachine(...)` are never a substitute for a permission decision. Do not invent a FakePlayer equivalence.

## Authoritative enrollment and use policy (proposed; F1)

**Enforcer to implement:** a Modular AI Robotics server-side action gateway plus a server-side endpoint/network policy registry. The registry must bind the original requesting principal and owner, work-order and stable request ID, enrolled bridge endpoint and dimension, validated attached AE2 network identity/fingerprint (if obtainable), approved operation IDs, work zone, item/quantity limits and revocation epoch. The same server-only policy must authorize before enrollment **and** before each network action. A user enrolling a bridge attached to another user's grid is not automatically entitled to that grid.

| Operation | Proposed server enforcement before touching AE2 or custody | Fail-closed outcome |
| --- | --- | --- |
| Enroll | Authenticate actor, validate owner/admin grant for *this endpoint and attached network*, work-zone/server rules, applicable independently verified claim/protection decision and stable network binding | `BLOCKED` if owner/network right or binding cannot be established, including absent/unknown provider where that right depends on it |
| Inspect stock/craftability | Gateway rebinds endpoint and network on the live server, then checks active owner/principal, `inspect` scope, provider decisions, revocation, loaded state and resource bound | No stock disclosure on denial; `BLOCKED` |
| Extract | Same checks for *this item/key, amount, source and receiver* plus hardware and verified physical mutation path | No extraction or credit on denial; `BLOCKED` |
| Submit craft | Same checks for specific pattern, item/key/quantity, work budget and durable request identity; only then create an AE2 action source representing the already authorized provenance | No submission if authorization, linked requester or deduplication proof is missing; `BLOCKED` or `RECONCILE_REQUIRED` if a prior submission may exist |
| Incoming `insertCraftedItems` / terminal `jobStateChange` | Requester adapter enters the **same server policy/custody boundary**, matches persisted request + link + network + endpoint + owner, applies current revocation and accepts only physical capacity | Unmatched/unauthorized `MODULATE` accepts `0`; previously accepted cargo is retained; terminal event changes only justified request state |

**Authority separation:** Actor identity is not user consent; consent is not proof of network control; an exposed AE2 capability is not ownership; `IActionSource` provenance is not a grant; a protection provider decision is separate from Modular AI Robotics' owner/zone policy and from any *verified* AE2 permission check. The core must enforce its own server-owned operation policy even with no claim mod. If any required independent network-owner/claim authorization cannot be proven, block the affected operation. Missing, unknown, errored or changed provider must not become `allow`; where a provider is applicable, fail closed until a supported and policy-consistent decision exists. A real provider's documented allow is necessary only for the scope it governs and never sufficient by itself.

On revocation, network/bridge replacement, cross-dimension move, changed attached grid, unavailable protection provider or world reload, **revalidate before each read/mutation and callback**. Old enrollment IDs must not authorize a changed network. Do not claim a universal AE2 network-owner API unless the exact tagged path and protection-provider integration have been established. **Block specialized operations until that binding is proven.** Tests: `INT-09`, `INT-09A`, `INT-09B`, `INT-09C`.

## Receiving and custody contract (proposed; F2)

**Provisional default:** one **server-owned, persistable staging inventory attached to the enrolled bridge** is the only intended `ICraftingRequester` receiver. AE2 never writes directly into a robot's cargo or another owner's arbitrary storage through this callback. Staged items remain bound to their original owner, `request_id`, work order, endpoint/network fingerprint, external crafting-link ID and per-key output allocation; later transfer into robot cargo requires a separately authorized, accounted operation. An alternative robot-cargo receiver is not selected for the first AE2 adapter. Implementation must establish inventory ownership, actual save/flush semantics, network identity availability, capacity, concurrency and rollback/reconciliation before enabling this receiver.

**Every callback is a potential authoritative mutation path, even if AE2 calls it without a controller request at that instant.** The server-side requester adapter must route callback entry through the gateway's non-model authorization and custody checks; an event handler must not bypass them. The tagged interface does **not** prove callback thread, tick confinement, reentrancy rules, callback retry behavior or atomic persistence. Until a verified synchronous server-thread-safe handoff is demonstrated, accept **zero** in `MODULATE` (and do not mutate state in `SIMULATE`); do not assume that queueing to another tick permits reporting acceptance now.

- **`SIMULATE`:** calculate the quantity currently acceptable using read-only policy/capacity snapshots. Return a bounded number between `0` and the requested amount; make **no inventory, ledger, work-order, enrollment, permission or durable-state mutations**. No reservation or accepted-cargo credit is created by simulation. A later modulation revalidates all conditions.
- **`MODULATE`:** on the authorized server thread, verify request/link/key, principal and owner, live endpoint/network attachment, operation scope, claim provider and revocation, capacity and item identity. Physically insert no more than available staging space and allowed outstanding quantity; return **only the actual amount inserted** (zero for denied, full, unloaded, mismatched or uncertain conditions). Keep any unaccepted output outside the staging inventory and **never** credit it as received. Partial callbacks update physical custody and per-key accepted counts; validate counts after mutation rather than assuming a requested amount was delivered.
- **Accounting record:** retain `request_id`, canonical intent, owner and principal, endpoint/network binding, external crafting ID/link serialization as available, expected per-key output, actual accepted per-key output, physical staging contents, subsequent proven robot/sink transfers, outstanding/uncertain output and cancellation/revocation state. The record is durably retained through terminal link invalidation. Do not report `COMPLETED` until specifically promised cargo is physically reconciled to its approved endpoint and work-order postcondition; `ACCEPTED_PENDING` only confirms a submitted external job.
- **Partial/terminal:** Multiple callback deliveries can precede terminal state. `jobStateChange` distinguishes `isDone()` from `isCanceled()` where the tagged link state is available, then stops treating the live link as usable. Preserve a durable tombstone/reconciliation record and all accepted staging items, even when canceled. A dead link is not proof all items were delivered; never reset the accepted count, discard cargo or auto-complete solely on the terminal event.
- **Revoked/changed/unloaded:** Reject new unauthorized or unobservable `MODULATE` deliveries with actual return `0`, request cancellation only through a verified safe path, record a block/uncertainty reason, and **quarantine by policy flag** previously accepted staging cargo pending authorized release/reconciliation. Do not silently redirect, destroy or return previous cargo. Unloaded endpoints cannot promise capacity or acceptance.
- **Durability limitation:** AE2 callback insertion, actual world inventory persistence and the project's request ledger may not be atomic across a crash. A pre-write log, a NeoForge transaction or serialized link **does not prove** that all were flushed together. Until a tested write-order and fault/reconciliation strategy handles callback-before-ledger and ledger-before-inventory crash windows and possible callback retries, advertise this feature as **blocked/unverified for crash-safe delivery**. Never acknowledge more than provably inserted; if crash persistence cannot be proved, preserve `RECONCILE_REQUIRED` and require manual/admin intervention rather than claiming exactly-once delivery.

Tests: `INT-10A`, `INT-10B`, `INT-10C`, `INT-11`, `INT-11A`. Only the tagged method semantics above are sourced; exact server-thread scheduling, duplicate callback guarantees, observed stock permissions, third-party claim-provider hooks, staging persistence and atomicity are implementation questions.

## Phased acceptance

**Phase A — authority and observation:** Prove compatible binary/startup isolation and a genuine server-verifiable network enrollment/ownership/claim path; inspect authorized stock only and prove cross-owner, changed-network, no-provider, provider-deny and provider-error refusal. No crafting submission. Gate `INT-07`, `INT-08`, `INT-09`, `INT-09A`, `INT-09B`, `INT-09C`.

**Phase B — bounded asynchronous craft and custody:** Nonblocking asynchronous plan, budget checks, authorized action-source provenance, persistent requester mapping and one bounded submission; implement staging receiver callback authority with correct `SIMULATE`, partial `MODULATE` and cancellation. Gate `INT-10`, `INT-10A`, `INT-10B`, `INT-10C`, `INT-12`.

**Phase C — interruption and reconciliation:** Persist live link through supported interface and expose it through `getRequestedJobs()`, reconcile after unload/restart/lost submission response, retain terminal receipt and accepted staging cargo, prove duplicate prevention and callback crash behavior. Gate `INT-11`, `INT-11A`, `INT-13`. No runtime claims until these tests actually pass.

## Class-loading, version and uncertainty gates

AE2-dependent classes remain in guarded integration-only code; core initialization, public DTOs, serializers and unconditional registration must not link them. NeoForge [26.1 mod metadata](https://docs.neoforged.net/docs/gettingstarted/modfiles/) documents that optional dependencies can still check versions when installed. Validate absence, compatible, disabled and present-incompatible combinations and make no claim of graceful fallback where the loader itself rejects installation.

Before implementation, maintainers must decide: (1) independently verifiable network authority/enrollment and any claim-provider hook; (2) how AE2's synchronous callback interacts with server-thread confinement and reentrancy; (3) staged receiver persistence/flush and crash fault harness; (4) whether AE2 retries an unacknowledged/replayed callback, and how to deduplicate by verified physical effects; (5) true capability of link reattachment/cancel/recovery for this tag. Any gap that can cause a forbidden effect, false acceptance or duplicate delivery **blocks that advertised AE2 feature**; `NOT RUN` tests cannot be marked `PASS` by document review.
